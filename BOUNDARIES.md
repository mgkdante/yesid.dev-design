# Product boundaries

yesid.dev-design shares reusable mechanics, not product decisions. Each product keeps policy, copy, runtime authority, data contracts, and behavior that cannot satisfy the [governance laws](README.md#governance-laws) without an app check. Similar code is evidence to inspect, not permission to promote it.

This is a receipt index, not a replacement for the owning decisions and tests. Consumer receipts were read at each product's canonical source state on 2026-09-01: Transit `ee2e565c86df4ffa40f11fcffb2ae23b56410a4e` and yesid.dev `8e23e70bcd564de09ac52f09141a9a848a128180`, both at design `v0.13.1`. Root placement is a deliberate trade: full CI on a docs PR versus `docs/` docs-only classification.

## Changing a boundary

A boundary moves only through a deliberate change that updates this card and the owning receipt. Shared code must remain app-neutral; a composed component additionally needs three independent consumers with the same contract. Package tests or Gallery success never substitute for each consumer's generated-output, test, build, and relevant browser proof.

`DECISIONS.md` records current public architecture contracts, `CONSUMERS.md` the observed adoption registry, and `packages/ui/README.md` the durable UI package and compatibility contract. This file maps current ownership across those receipts; it does not supersede them.
